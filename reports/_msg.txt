PHASE 12 HARNESS: native categorical splits in the winning LightGBM extra_trees family

THE HYPOTHESIS
Our strongest single family is LightGBM extra_trees=True. The 285-column full view carries raw
categoricals and numeric copies, but LightGBM sees them as plain numbers, so its ordered
target-based categorical split algorithm has never been exercised inside the winning configuration.
CatBoost's native CTRs were worth +6.64e-5 at model level, and LightGBM's mechanism is DIFFERENT: an
ordered shrunk target statistic with cat_smooth/cat_l2, not a CTR with priors. This asks whether
native categorical splits improve the extra_trees family WITHOUT removing the existing 48-column
competition TE block.

This is NOT the public notebook's failed experiment. That substituted numerics-as-categories
INSTEAD OF target encoding and confounded learning rate and seed. Here the te_ block stays
byte-identical and only the split algorithm changes, so L0 -> L1 is a clean single-variable test.

WAS NATIVE LIGHTGBM CATEGORICAL HANDLING ALREADY TESTED? (checkpoint Q2)
No. A ledger scan finds no lgbm entry anywhere declaring categorical_feature, and neither
src/features/s6e10.py nor src/features/view.py ever emits such a flag. The only prior native-
categorical work in this campaign is CatBoost (Phase 10B and 11R), a different library with a
different mechanism. This is genuinely new, not a re-run.

THE AUDIT WAS NECESSARY, AND IT CAUGHT A DETECTOR THAT WOULD HAVE CLOSED THE PHASE EARLY
scripts/audit_lgb_native_cat.py answers each question from the FITTED MODEL rather than from
parameter docs, because docs describe intent and the dump is what ran. My first version counted the
substring "||" to detect categorical splits and reported ZERO for every configuration, including one
where the declaration had demonstrably worked. LightGBM's dump_model() renders both one-hot and
subset categorical splits as decision_type "==" with an integer threshold; only the saved model
TEXT file uses pipe-joined category lists. A wrong detector reported a working treatment as inert,
which is precisely the failure that would have closed Phase 12 before it started. The discriminator
is now decision_type, and every conclusion is cross-checked against a forced synthetic probe where
the categorical is the ONLY signal, so "the split lost the gain race" can never be mistaken for
"the declaration did not take effect".

  A1  categorical_feature works on this CPU build, by index and by name. Forced probe: undeclared
      gives 64 splits all of decision_type "<="; declared gives 125 all of "==".
  A2  requirements met on the real view: all 7 audited columns are non-negative integers, zero NaN
      on fit and apply rows, and every apply-row code is present in the fit rows.
  A3  NaN in a declared categorical is routed as MISSING, not as a category. Proven from the model
      itself: feature_infos carries LightGBM's internal missing marker -1. A missingness sentinel
      therefore cannot silently become a real level.
  A4  extra_trees does NOT disturb the categorical search. A forced probe gives 125 categorical
      splits with extra_trees=True and 125 with False -- identical count, identical code set.
      extra_trees randomises the NUMERICAL threshold search only. The two coexist, so categoricals
      can be tested inside the winning configuration rather than only outside it.
  A5  by cardinality (forced probe): levels 2/3/4/5/6 give 25/41/75/100/125 categorical splits.
  A7  this CPU build supports categorical splits.
  On the REAL 285-column view, declaring META4 produces 58 categorical splits against the control's
      0, so the treatment is OBSERVABLE and not inert.

A MECHANISTIC PRIOR RECORDED BEFORE THE RUN, NOT AFTER
cat_smooth=10 and cat_l2=10 make a LightGBM categorical split a SHRUNK target statistic with an
explicit prior. That is the same smoothing family our 48 te_ columns already supply in the same
matrix. The expected effect is therefore SMALL rather than new information. Stated in the runner's
own output before any result, so a small outcome is a prediction met rather than a surprise
reinterpreted afterwards.

FOUR BUGS FOUND WHILE BUILDING THIS, ALL FIXED, ALL WORTH RECORDING
1. The split detector (above). The most dangerous of the four: it produced a confident ZERO for a
   treatment that worked.
2. SURVEY13 used raw-dataset spellings. Three of the thirteen -- "In-flight entertainment",
   "WiFi service", "In-flight service" -- do not exist in the view, whose spellings are "Inflight
   entertainment", "Inflight wifi service" and "Ease of Online booking". Declaring an absent column
   raises KeyError, so column names are now resolved against the view rather than trusted from the
   raw header.
3. splits_on_declared looked up int-keyed counts with string keys and so reported 0 splits on the
   declared META4 columns when the true count was 58. A reporting bug that would have read as "the
   treatment does nothing" -- the same false negative as (1), reached by a different route.
4. roc_auc_score was imported only inside report(), so the training path raised NameError at the
   first AUC computation.

WHY THE CATEGORICAL HYPERPARAMETERS ARE PINNED
cat_smooth, cat_l2, max_cat_threshold, max_cat_to_onehot and min_data_per_group are written out
explicitly. Left implicit, m.params returns None for every one of them, so the run record would not
contain the values that governed the result and the arm would silently depend on whatever the
installed library defaults to.

SAFETY CHECKS RUN BEFORE EVERY ARM, ANY FAILURE ABORTS (the 10 required assertions)
