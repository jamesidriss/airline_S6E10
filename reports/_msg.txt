MECHANISM: cat_smooth=10 and cat_l2=10 make a LightGBM categorical split a SHRUNK TARGET STATISTIC --
the same smoothing family the 48 te_ columns already encode from the same columns. The extra_trees
family already randomises its split search aggressively, so there is little for an ordered
categorical search to add that survives averaging over 59 members. The audit predicted a small
effect BEFORE the run; the measured marginal is smaller still, which is the prediction confirmed
twice over.

One asymmetry recorded: META4's 2-3 levels sit at or below LightGBM's max_cat_to_onehot default of
4, so those columns receive ONE-HOT rather than subset splits. L1 is therefore not a strict subset of
L2's test.

THE AUDIT WAS NECESSARY, NOT CEREMONIAL
My first audit detected categorical splits by counting the substring "||" and reported ZERO for every
configuration, including one where the declaration had demonstrably worked. LightGBM's dump_model()
renders both one-hot and subset categorical splits as decision_type "==" with an integer threshold;
only the saved model TEXT file uses pipe-joined category lists. A wrong detector reported a working
treatment as inert, which is indistinguishable from a genuine negative and would have closed Phase
12 before it started. Corrected detector, on a forced probe where the categorical is the ONLY signal:
undeclared gives 64 splits all "<=", declared gives 125 all "==".
extra_trees=True and extra_trees=False give IDENTICAL categorical split counts (125 and 125, same
code set), so extra_trees randomises only the NUMERICAL threshold search and the two mechanisms
coexist -- which is what makes the test possible inside the winning configuration at all.
NaN in a declared categorical is routed as MISSING, proven from the model itself: feature_infos
carries LightGBM's internal missing marker -1, so a missingness sentinel cannot become a real
category code.

THREE BUGS, ALL MINE, ALL WITH EVIDENCE
1. The split detector described above.
2. TWO fold-index coincidences, both invisible on fold 0. The champion uses a FIXED seed and
   inner_seed=k; I used seed+k and inner_seed=0, which coincide on fold 0 (1+0 == 1, k=0) and
   diverge after. L0 measured +0.0001e-5 on fold 0 but +4.4984e-5 and -6.5733e-5 on folds 1 and 2.
   Fixing the seed alone still left the mismatch, and that residue is what exposed inner_seed. A
   fold-0-only screen cannot detect either, so the control-reproduction check now runs on EVERY fold
   and tests pin the fixed-seed and inner_seed=k conventions against run_xt_zoo.py.
   This is the transferable lesson: any fold-indexed convention reproduces correctly on fold 0 by
   default.
3. A te_ reference compared ACROSS folds. te_ columns are refitted per fold, so the check aborted
   with "te_ columns changed vs control" on a perfectly correct run. Now keyed by fold, which makes
   it assert the property that actually matters -- every arm of a fold received identical features.

METHODOLOGICAL FINDING TO CARRY FORWARD
A three-fold screen overstated the effect by 3.1x. Folds 0-2 gave L2 +5.87e-5; five folds gave
+1.89e-5. L1 went the other way, +3.47e-5 to -2.10e-5. Fold-level spread here is several times the
mean, so FIVE FOLDS IS THE MINIMUM for a standalone claim on this competition. Both statistics are
printed side by side in reports/p12_final.json so the gap stays visible. This is the second instance
of the same failure mode as Phase 11R's gate B: a criterion satisfied for a reason that carries no
weight.

A PUBLIC-NOTEBOOK PROVENANCE CORRUPTION, FOUND AND FIXED
Pulling three kernels into one shared directory produced a single file containing a DIFFERENT notebook
than the one already audited, while still carrying the audited notebook's filename. Had the audit
been re-run, a notebook's findings would have been attributed to the wrong author, and existing
ledger entries referencing that filename would have silently become wrong. Same class as the earlier
path-assumption bug -- trusting an output filename instead of verifying identity -- but worse,
because the misfiled content was already referenced by ledger entries. Each kernel now gets its own
directory, and identity is cross-checked three ways: per-kernel directory, kernel-metadata.json id,
and the notebook slug in the filename, with a mismatch a hard failure. The sachith7 notebook
re-pulls to 30 cells / 29222 chars / sha16 9fdae7c2e42ca6d526, matching the original audit exactly,
so its recorded findings stand.

STRONGEST REMAINING DIRECTION: AUXILIARY-TASK EXPECTED-VALUE FEATURES
Two independent public sources converge on a mechanism our 285-column view does not contain.
goodpjw2008 trains 16 auxiliary models, each predicting ONE rating from the other 20 columns with no
satisfaction label, and uses the expected value sum_k k*P(k) per rating as 13 new features:
+13e-5 on one XGBoost, +9e-5 on one LightGBM, +5.9e-5 on the stack with all five folds up.
sachith7 independently uses "aux expected ratings" computed once over train+test. Our view has 48
te_ + 54 ogte_* + 2 teach_*, but our teacher predicts SATISFACTION from the original dataset, which
is a different mechanism -- there is no per-rating auxiliary target here. It is label-free, so it can
be fitted fold-safely with no new infrastructure, and goodpjw2008 narrows the target precisely: the
SURPRISE features from those same auxiliary models do nothing, only the plain expected value helps.
